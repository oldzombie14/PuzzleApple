## 目标与范围

这是一份架构层面的文档：先定各层的职责和层与层之间的接口，语法和生效性判断做成可替换的模块，具体规则以后可以继续改。依据 2026-11-19 的 V5 分支代码、V5.md、C2C 文档，以及 11-19、11-20 的讨论。

- 分三部分：第一部分是纯架构与说明（带小例子）；第二部分是当前开发情况：已定语义、与现有实现不一致之处、修改建议；第三部分是新增设计时的考量清单与协作方法，供 ice 和 Astra 在加新东西时逐项检查。
- 不改组句面板 UI；结构迁移先承载现有进度锁、薄膜门、方案 A 暂停和游戏流程。命令参与对象与范围策略的已确认变更统一见[重构前问答](句子系统架构-QA.md)，行为变更单独验收。
- 语法和生效性判断还没定稿，架构把它们做成可替换的模块。

## 第一部分：架构与说明

### 设计原则：解耦与可替换

语法和生效性判断还会反复改，所以各自是独立模块，只通过固定接口和其它层交换数据；改它们不需要动范围、调度、表现和镜头。

| 模块 | 输入 | 输出 | 可以自由改的部分 |
| --- | --- | --- | --- |
| 语法 | 一串词 | 是否成立 + 意图（动作、主语性质、目标性质、句型类别、范围策略） | 词类、句型模板、例外表，甚至整套解析方式 |
| 范围 | 玩家位置、进度锁、薄膜、门开度、跨章 | 当前可涉及的实体集合 | 范围策略：默认池、全局、下令时快照、自定义 |
| 生效性判断 | 意图 + 一个实体 | 接不接受、会不会变化、写入哪个输出端、与已有意图是否冲突 | 每个词、每类实体的判断规则与冲突规则 |
| 表现 | 实体 + 已接受的意图 | 动画、完成状态、镜头请求 | 每个实体自己的表现组件 |

调度层只做编排（谁先成立、何时分发、何时归库、暂停与恢复），不判断具体规则。

个案写在哪里：

| 个案类型 | 写在哪里 | 现有例子 |
| --- | --- | --- |
| 语法 | 该句型或词条自己的规则条目：模板给默认，条目可禁用或改写 | door move light 只给弱涟漪 |
| 影响范围 | 规则声明的范围策略 | light world、no move 全局；一次性命令的范围策略见[重构前问答的命令范围策略](句子系统架构-QA.md#命令范围策略) |
| 对象条件 | 实体的生效性判断 | 充能门未满能不开；暗方块不被 light move 接管 |
| 表现 | 实体的表现组件，优先级「实体 + 规则」专用 > 实体默认 > 输出端默认 | off light 时星芒缩小消失，方块灯渐暗 |
| 冲突 | 输出端策略，特例声明在规则或实体上 | on door 先完成，再恢复 door move |
| 镜头 | 实体的关键机关提示 | 充能门只在能开时展示 |

约束：

- 通用层（范围池、调度、镜头导演）的代码里不出现具体词、句式或物体名字；需要特例时，先在对应模块里加扩展点。
- 新规则可能改变旧规则的结果。规则写成数据和独立判断后，用一个编辑器面板列出「每种词组合 × 每类实体」的当前判定，改动前后一对比就能看出影响了哪些旧规则。
- 每条规则配独立检查，改动后全部重跑。

### 六层结构

句子说出后变成与场景无关的意图，调度层从范围池取出当前能涉及的实体逐个分发，实体自己决定表现，并把变化、完成和镜头请求交回。

结构图（文字版）：

```
组句区（玩家说出的句子）
   → 语法数据库（词类 + 句型模板 → 意图）
   → 调度层（冲突、命令生命周期、暂停）
         ↑ 池中实体
登记层（实体：归属空间 + 性质） → 范围池（薄膜 ∩ 进度 ∩ 门连通）
调度层 → 逐个分发意图 → 表现层（实体按输出端执行）
   表现层 → 镜头请求 → 镜头导演（当前空间的关键机关）
   表现层 → 变化与完成情况 → 反馈与归库（带星、弱涟漪、命令完成）
```

意图 = 动作（on、off、move、照亮、mirror、no）+ 主语性质 + 可选目标性质 + 句型类别（持续／命令／世界流程）+ 输出端与目标值。

| 层 | 职责 | 现有对应 |
| --- | --- | --- |
| 登记层 | 实体组件在生成时登记、销毁时注销；记录归属空间（副本的控制跟原件、所在位置另记（照亮所在空间用），会跨空间移动的实体刷新空间）、性质（天生／状态／句子授予，查询时现算）、输出端列表、是否关键机关 | SentenceEntity／SentenceEntityRegistry 已登记灯体、灯群控制器和门；性质与输出端用资产标识，灯体的 light 性质按实际亮度现算；现有共同渐变仍共享一个输出端，星群保持群体实体；SentenceOwnership 表达副本归属 |
| 范围池 | 由薄膜、进度锁、门开度、跨章、关盒隔离算出可涉及空间，筛出实体；事件触发重算，只回答「能涉及谁」 | SentenceScopePool 使用 SentenceSpace 资产缓存连通图；ProgressLock 订阅 IProgressBoundary 状态事件，MembraneDoor 使用空间资产提供区域；旧运动／效果接口暂经 LightSpace 兼容映射接入 |
| 语法数据库 | 词类、句型模板、例外表；先判语法有效性，再交调度判场景生效性 | SentenceGrammar 生成动作、主语／目标性质、句型和范围策略；灯／门开关、运动分发、照亮与世界流程按意图路由。原生句式的兼容信号从意图生成，CognitionRule 暂保留绑定和冲突声明；运动控制器和输出归属直接读取主语与目标性质，mirror 显式沿用原规则。开发核对工具独立于 Unity 运行时 |
| 调度层 | 说出、冲突、持续与命令、命令参与对象与范围策略、方案 A 暂停；池或性质变化时做差集重分发；汇总反馈 | SentenceRuntime + 四个 Effect 处理器 |
| 表现层 | 实体按输出端执行意图；共性组件复用（渐变、铰链、漂移、停靠、轨道），特例组件覆盖；群体实体管星群、灯群 | SentenceStateOutput 承载发光、铰链、升降的开关、变化、完成、暂停与释放；SentenceMotionOutput 承载运动资格、范围内指令、示范接管记录与运动修订号，轨道平台及 Intro／章节灯光控制器已读取登记的位置输出，三类室内门往复读取各自运动输出并保留原开关优先级，充能门循环由输出通知启动；室外灯群、门与地面按控制组件独立登记，门亮灭通过状态输出执行，均由输出推送至原控制器 |
| 镜头层 | 默认不锁视角；关键机关在实际变化时提交 focus 请求，导演只在玩家当前空间挑一个 | SentenceFocusSource 按机关生命周期登记展示空间与变化请求；SentenceCameraDirector 在玩家当前空间和效果范围的交集中选择目标，SentencePresentation 使用统一时序。原有机关资格在绑定层适配，逐句镜头表已移除；无请求时仍播放保持当前视角的演出，Chapter I 同样保持当前视角 |

light world、no move、world on/off 走全局通道，不进范围池。

### 冲突：按物体输出端判断

以下是生效性判断模块的默认冲突规则，可整体替换。冲突发生在「同一物体的同一输出端上目标值不同」，不再按句子通道全局判断，也不逐句标注冲突句。输出端做成数据定义，以后新特质只加定义或组件，冲突逻辑不变。

| 输出端 | 值类型 | 写入它的意图 | 已知实体 |
| --- | --- | --- | --- |
| 发光 | 连续亮度，两层叠加（自身状态 + 句子授予） | on/off light 写自身层；light X 写句子层；light light 乘倍率 | 灯体、星芒、光源化的门与地面 |
| 铰链 | 开合角度 | on/off door 开关；door move、光源化门上的 light move 摆动 | 白门、房间 3 入口门 |
| 升降 | 高度 | on/off door、door move | 充能门（另有满能条件） |
| 位置 | 运动（自由、轨道、定向停靠） | X move、A move B | 灯、星芒、平台、室外地面 |
| 镜像 | 副本存在／游走 | mirror mirror、mirror move | 角镜、入口镜 |

规则：

1. 同一输出端上目标值相同则共存，不同则先成立者赢；输出端不同则互不干扰（on door + off light 不冲突）。
2. 输出端自带策略：铰链与升降上「命令临时压过持续，完成后持续恢复」，即现在 on door 先完成、door move 再恢复往复的做法。
3. 一句话可以在部分实体上生效、部分被挡。只要有一个生效就正常显示，全部被挡才显示冲突。
4. 只有真正的特例写进例外表，如充能门未满能不响应开门。
5. 仅组句区层的状态冲突（如 on light 与 off light 同时站着）仍按语法模板的互斥关系判定。

### 状态与存档

每个实体的每个输出端都能导出、恢复自己的状态；方案 A 暂停和以后的存档共用这份数据，存档不需要返工。

- 实体：位置、方向、相位、进度、两层亮度、停靠状态、是否已被玩家接管（示范运动）。
- 世界：进度锁解锁状态、门开度、章节完成状态、自建灯与镜像副本的生成记录。
- 组句区：句子、说出状态、成立先后、命令的范围策略与参与执行状态。词库、笔记、快照、历史。
- 不存：范围池和性质都由上面的状态重算得出，只存来源。

输出状态的已接入范围和下一项工作统一见 [V5 当前进度](../V5.md#进度与验收边界)。

## 第二部分：当前开发情况

### 当前已定的语义

light 指「光」本身：on/off light 作用于空间（让这里有光／没光），其它 light 句作用于此刻存在的光。以下是讨论中已确认的规则。

| 主题 | 规则 |
| --- | --- |
| light 性质 | 发光亮度大于 0 即算 light；淡出过程中仍算，完全暗下才失去。light move、收集 light、充能都只看这一层。 |
| 潜在发光体 | 隐藏登记一层「能发光的地方」（灯体、星芒等），on/off light 开关它们。门、地面不在其中。暂不给外观提示。 |
| 光的两种归属 | 潜在发光体的光受 on/off light 控制。门、地面只在 light X 生效期间有光，这道光归句子所有，拆句后淡灭；这期间 light move、light light 能作用于它。off light 不熄它，门光只受 light door 控制。 |
| 性质来源 | 天生（门是 door）、状态（亮着是 light）、句子授予（light door 生效时门是 light）。一个物体可同时有多种性质。 |
| move | 由物体结构解释：无约束布朗运动，铰链摆动，轨道往返，位置锁死的不动。光源化的门被 light move 时原地摆动，与 door move 表现一致。 |
| floor | 首次从平台收集后，所有地面都能收 floor，light floor 对所有地面生效；只有平台能动（沿轨道），其它地面位置锁死。 |
| 自指 | 物体不能以自己为目标；light move door 时光聚向门，门自身的光不参与聚集。 |
| light light | 增亮范围内所有此刻存在的光，包括句子给出的门光、地面光。 |
| 点击收词 | case by case：充能门首次点击授予 light door 例句，之后亮时显示 light door、完全熄灭时显示 door；镜像副本可能只显示原物体的词。由物体自己配置。 |
| 一次性句的执行资格 | 点击时先检查全局判定锁、冲突和当前作用范围。只在至少一个对象能开始动作时取得锁。有效句冲突或命令无可执行变化时退回草稿，条件恢复后重新提示点击。 |
| 部分生效 | 只要有一个对象生效就算生效（带星与否看是否有可见变化），全部被挡才显示冲突。 |

持续句的现有范围规则：范围 = 当前薄膜区域 ∩ 已解锁进度；带门的进度边界解锁后，只在门开度大于 0 时连通；light world 与 no move 全局生效。一次性命令的参与对象与范围策略统一见[重构前问答 Q1 及命令范围策略](句子系统架构-QA.md)。

持续句只对当前范围内的东西生效，超出范围的东西恢复为没有这句话时的样子。例：玩家离开后门不在范围内，门显示为没有 light door 时的样子，也就不算 light。

### 已确认差异的落实情况

| 项目 | P5 当前行为 |
| --- | --- |
| light 收词 | 房间 1 地灯、教学球及章节灯按当前亮度判断。通道亮星按单颗星的轮廓与可见性命中，遮挡仍然有效。 |
| 教学球的 light 性质 | 实际亮度大于零时可以收词并响应移动；完全熄灭后退出 light 移动，原有暗球示范按教学规则执行。 |
| 句子赋予的光 | 发光门和地面可接受 light move，沿用自身结构的运动。充能门第一次点击授予例句，之后按当前门光显示 light door 或 door。 |
| light light 的对象与反馈 | 范围内亮着的实体或地面光能产生带星反馈，句子赋予的门光、地面光也受增亮。 |

P5 原生运动句已按实体登记的运动输出分配。共享运动方式的星群和灯群各自保留群体输出；轨道球与可自由移动的生成灯分开登记。实现和检查入口见 [V5 当前进度](../V5.md#进度与验收边界)。

### 对当前实现的修改建议（分步）

分六步，每步保持现有行为，按 [V5 句号生效设计](../V5.md#句号生效设计) 跑完对应检查再进下一步。这六步保持原有 UI 与玩法流程。结构就位后，按上表已确认的玩法差异分别实现和验收。

1. **登记 + 范围池**：加实体组件，把 ProgressLock、MembraneDoor 的计算包进范围池，改为事件触发；进度锁改成引用统一的门接口，去掉按门类型分开的字段。空间标识从写死的 LightSpace 枚举换成场景里的空间资产。
2. **灯与门的开关**：LightStateEffect、DoorStateEffect 的手写 Targets 改为查池；引入发光、铰链、升降三个输出端。
3. **运动**：MotionEffect 的按空间 if 链改为位置输出端，把各对象自取 HasEffect 逐个换成调度层推送。
4. **镜头**：SentencePresentation 改为导演 + 关键机关提示，去掉按句式的镜头表和代码特判。
5. **语法数据库**：给词标词类、建句型模板与例外表，由模板生成意图，逐步替换 CognitionSignal 枚举；组合判定保留自动检查入口，开发核对与提需使用独立 HTML 工作台，平台修改另开会话。
6. **状态集中**：输出端状态统一导出／恢复，方案 A 暂停改用它，为存档做准备。

## 第三部分：新增设计时的考量

加一个新词、句式、物体或空间时，按层逐项回答下面的问题。答不出的就是要问 ice 的地方；Astra 在动手前把答案和未决项一起列出来。

### 考量清单

1. **语法**：这个词属于哪类（状态词、身份名词如 door、现象名词如 light、动作）？和哪些已有词能组合，哪些组合要列为例外？是持续句、命令句还是世界流程？
2. **性质**：新物体天生有哪些性质？哪些状态会让它获得或失去性质？哪些句子能授予它性质，授予的性质（如光）归谁控制？
3. **范围**：走范围池、全局、下令时快照还是只看玩家当前空间？跨薄膜、跨章、门关严时怎么处理？副本的控制按原件，照亮按副本自己所在的空间。
4. **生效性**：对每类已有实体，这个意图接不接受、会不会变化、写哪个输出端？和已有句子在同一输出端上是否冲突？部分生效时怎么反馈？
5. **表现**：用现有共性组件还是新特例组件？暂停时要保存什么（方案 A）？
6. **镜头**：是不是关键机关，要不要 focus？
7. **收集**：点击它收到什么词或例句？已知时怎么反馈？
8. **对旧规则的影响**：这次改动让哪些已有词组合、哪些实体的结果变了？逐条列出给 ice 确认。
9. **状态**：新状态能否导出、恢复（存档与暂停）？
10. **检查**：新增哪些检查？哪些旧检查的断言要随规则改，逐条说明。

例：加入 light door 时，第 2 项的答案是「门不是潜在发光体，句子生效期间有光，这道光只受 light door 控制」；第 8 项就会列出 light move、light light、收集 light 三处的结果变化——这些组合应随新实体一起验收。

### 协作方法

1. **文档各管一件事**：V5.md 写「规则是什么」，本文档写「东西放在哪一层」，C2C 写单次交接。同一件事只写一处。
2. **交接单固定四项**：改的是什么、受影响清单（按上面第 8 项列）、明确不改的东西（UI 和流程默认不改）、验收方法。受影响清单先给 ice 过目。
3. **按清单回报**：Astra 完成后逐项勾选，没覆盖到的明确说出来。
4. **重构期间结构和玩法不同时改**：先按第二部分的步骤换结构、保持行为，再处理不一致清单和新语义。

### 尚未进流程的设计：mirror 与镜像副本

以下是 ice 已定的方向（11-20），还没写交接文档，也没做进流程。用户本轮明确暂不处理 mirror 语法及相关细化，等开发到此流程、出现问题时再审查。开发到这部分时按这里的逻辑走，细节以届时的 C2C 交接文档为准。

- **mirror 的语法**：mirror 是名词，另有自己的语法。目前只做了 mirror【object】（镜像化），其特殊设计涉及镜像轴。整体和 door、light 差不多。door【object】语法还没设计，也可能不会有。
- **副本的控制跟随原件**：副本不直接接受控制，而是读原件的状态。例：副本是一盏灯时，on/off light 不直接开关它，它的亮灭跟原件一致。
- **副本照亮自己所在的空间**：副本所在空间如果在薄膜里，它可以照亮那个薄膜空间。也就是「受谁控制」跟原件走，「照亮哪里」按副本自己的位置算。
- **架构上的对应**：登记层给副本记两项，控制归属指向原件，空间位置按副本自身；发光输出端的值从原件读，照亮效果落在副本所在空间。范围池里副本跟原件一起被选中或排除。
